## 2. Контекст системы и границы

### 2.1. Утверждения

- **A-1.** Система включает: мобильное приложение (Flutter), бэкенд на Firebase, канал доставки push (FCM), **хранилище медиа** (изображения — **Supabase Storage**, **A-5**), механизм публикации контента (**интерфейс редактирования / админка** вне кода приложения — **A-29**), публичный веб-сайт с SEO (**БТ §4.1**).
- **A-2.** **Единый источник правды** по контенту сценариев и игр — данные, управляемые через админку и отдаваемые клиентам (МП и сайт) через согласованный контракт (**БТ FR-B-1, FR-B-2, FR-B-3, BR-2**).
- **A-3.** Пользователь МП **не аутентифицируется** на старте продукта; персонализация витрины и аналитика строятся без прямых ПДн в событиях (**SR-PRIV-1**, **§11.2**).
- **A-1a.** С **первого релиза** используется **единый брендовый домен** `scenario-games.ru`: публичный сайт, SEO-страницы, **fallback** шаринга и **те же URL** как **deep link / Universal Links (iOS)** и **App Links (Android)** — при установленном МП ссылка открывает приложение на экране сценария, иначе — веб-страницу (**БТ FR-M-7, FR-W-4**).

## 3. Архитектура высокого уровня (Firebase)

### 3.1. Утверждения

- **A-4.** **Firestore** используется как основное хранилище **опубликованного** контента для чтения МП и сайта: сценарии, игры, связи, метаданные витрины и групп (**БТ CR-4, FR-B-2**).
- **A-5. (Медиа — Supabase Storage на старте)** Файлы изображений карусели (**БТ CR-5**) хранятся в **Supabase Storage**. В документах Firestore — **URL загрузки** (или пути + разрешение URL в клиенте), порядок слайдов, тип кадра, подпись, **alt**. **На старте** это **основное** решение: Firestore + Functions + Supabase Storage, **Storage policies (RLS)**, готовые SDK (Flutter, веб), минимум операционной работы; раздача файлов идёт через инфраструктуру Supabase с кэшированием на стороне сети. Сочетается с целями по **LCP** при оптимизации веса и формата изображений (**NFR-SR-4**, **§13.1**). Причина: **Firebase Storage стал платным** — медиа перенесены в **Supabase Storage** (**ED-14**).
- **A-5a. (Опционально позже)** При росте трафика, требованиях к тарифам или гибриде с **AWS** допускается перенос объектов в **S3** (или S3-совместимое хранилище) с **отдельным CDN** — отдельное архитектурное решение и миграция URL в Firestore; до этого момента **Supabase Storage** остаётся источником правды для медиа.
- **A-6.** **Cloud Functions for Firebase** реализуют: (а) **серверные триггеры** при публикации нового сценария — постановка задачи на push (**БТ FR-B-4**); (б) **агрегацию окна** новинок для ежедневной отправки в 11:00 МСК (**A-7a**); (в) **валидацию** или денормализацию полей при записи из админки (**A-29, A-29a**).
- **A-7.** **Cloud Scheduler** (cron) вызывает функцию **ежедневно в 11:00 Europe/Moscow**, которая инициирует отправку уведомлений (**БТ FR-M-4**).
- **A-7a. (Редакционная политика push)** За сутки **не более одного** push на пользователя/устройство. Если за интервал между двумя запусками 11:00 МСК опубликовано **несколько новых сценариев**, в уведомлении отражается **только последний** по времени публикации (остальные пользователь видит на витрине в приложении).
- **A-8.** **Firebase Cloud Messaging (FCM)** — транспорт push на Android; для iOS — через APNs (настройка в Apple Developer + Firebase).
- **A-8a. (FCM topic — обязательно)** Массовая доставка push о новых сценариях выполняется **только** через **FCM topic** с фиксированным именем **`new_scenarios`**: после выдачи разрешения на уведомления МП вызывает `subscribeToTopic('new_scenarios')`; сервер в 11:00 МСК отправляет **одно** сообщение **на этот topic** (**A-32**). Коллекция FCM-токенов в Firestore **не ведётся** на первом этапе. При смене FCM-токена клиент **повторно подписывается** на topic при старте (идемпотентно). Переход на рассылку по списку токенов из БД допускается только при появлении требований к **сегментам**, A/B или персональному аудиту доставки — отдельное изменение системных требований.
- **A-9.** Основной **HTML-сайт** размещается на инфраструктуре, обслуживающей **scenario-games.ru** (SSG Next.js — **A-26a**). **Firebase Hosting** для главного сайта **не обязателен**; может использоваться для служебных страниц, редиректов или экспериментов. **Fallback URL шаринга** на `scenario-games.ru` обязан отдавать страницу сценария с OG-тегами (**БТ FR-W-4, FR-M-7**).

| Поле | Тип | Обяз. | Комментарий |
|------|-----|-------|-------------|

### 4.2b. Связь «сценарий ↔ группа смысла» (`scenario_semantic_groups`) — many-to-many

Отдельная коллекция, **источник правды** по участию сценария в группах и **порядку внутри группы** (**БТ §7.1**).

| Поле | Тип | Обяз. | Комментарий |
|------|-----|-------|-------------|
| `scenarioId` | string | да | Ссылка на сценарий |
| `semanticGroupId` | string | да | Ссылка на `semantic_groups` |
| `order` | number | да | Порядок сценария **в списке этой группы** (эксперт задаёт отдельно от порядка на витрине) |

Ограничение: пара (`scenarioId`, `semanticGroupId`) **уникальна**. Один сценарий может входить в **несколько** групп; группа «Сценарии прошлого» подключается тем же механизмом (`semanticGroupId` группы с `isPastArchive: true`).

**Запросы:** для экрана группы — выборка по `semanticGroupId` с сортировкой по `order` + join к `scenarios` (или денормализованные поля в связи для списка). Индексы Firestore под эти запросы — при проектировании схемы.

**A-4c.** Массив **`semanticGroupIds`** на документе `scenarios` **не использовать** как каноническое хранение; при необходимости денормализованный список ID допускается в `scenario_public_*` **только** как производное от **§4.2b** при публикации.

**A-10.** Денормализация для чтения МП допустима: при публикации сценария собирать «view model» документ `scenario_public_{id}` с вложенным списком игр и нужными полями, чтобы главный экран и экран сценария читали **минимальное число запросов**.
- **A-4a.** Тексты `whyTheseGames`, `shortDescription` и аналогичные пользовательские тексты в MVP — **plain text** (переносы `\n`); без WYSIWYG-разметки в клиенте.
- **A-4b.** Достаточно флага **`published`** (черновик / опубликовано) без UI отката версий в админке на первом этапе (**БТ FR-B-1** «желательно версионирование» — отложено).

### 4.4. Модель данных под чтение сайтом (Next.js SSG) и SEO

Публичные документы (или экспорт для билда) проектируются так, чтобы **статическая генерация** на Next.js получала за **предсказуемое и ограниченное число обращений** к данным всё необходимое для **готового HTML** страницы: контент, метаданные, перелинковку (**БТ FR-W-2, FR-W-1, NFR-2**).

- **A-10b.** **Потребитель модели — не только МП:** схема Firestore, денормализованные документы и/или артефакт экспорта (JSON) **согласуются** с контрактом Next.js: `generateStaticParams` (или эквивалент) по списку **опубликованных** `slug` сценариев и игр; одна страница — **не более согласованного бюджета запросов** (целевой ориентир: **1–2 чтения** на URL при использовании агрегатов `*_public` / `sitemap`-документов).
- **A-10c.** В данных для сайта доступны поля, достаточные для **`<title>`**, **`meta description`**, **Open Graph** (`og:title`, `og:description`, `og:image` — абсолютный URL, согласование с полями шаринга **FR-M-7, FR-W-4** где применимо), при необходимости **canonical**; для изображений — **`alt`** слайдов (**CR-5**) в HTML. Тексты тела страницы — в форме, пригодной для вывода в SSG **без исполнения клиентского JS** для основного контента (**A-4a**).
- **A-10d.** **Перелинковка без N+1:** в агрегате страницы **сценария** — упорядоченный список игр минимум со **`slug`** (и при необходимости `title` для якорного текста); в агрегате страницы **игры** — список связанных **сценариев** со **`slug`** (денормализация при публикации или отдельный индексный документ, пересобираемый функцией). Краулер и билд Next.js **не обязаны** выполнять цепочку запросов «игра за игрой» для построения меню ссылок.
- **A-10e.** Для **инкрементальной пересборки** (ISR `revalidate` или перезапуск билда по webhook) в публичных документах присутствуют **`updatedAt`** и/или **`contentVersion`** (связка с **A-44**).

| ID | Требование | Проверка приёмки |
|----|------------|------------------|
| **SR-SEO-1** | Модель данных и денормализованные «вьюхи» для публикации **удовлетворяют §4.4 (A-10b–A-10e)**; интерфейс редактирования позволяет заполнять SEO- и OG-связанные поля согласно схеме. | Демо-билд Next.js строит sitemap и все публичные URL без превышения бюджета запросов; в HTML есть корректные title/description/OG; перелинковка сценарии ↔ игры из данных без дополнительного N+1 |

## 5. API и контракт для мобильного приложения

### 5.1. Утверждения

- **A-11.** МП **читает** данные через Firestore SDK (слушатели/one-shot get) с **прямым доступом** к опубликованным коллекциям и **Firestore Security Rules** (read-only для клиента) — **допустимо и принято** для MVP; слой BFF (Cloud Function + CDN) вводить только при отдельных требованиях к скрытию схемы или жёсткому rate limit.
- **A-12.** Обязательные «вьюхи» для клиента: `home_feed` (витрина + ссылки на группы), `semantic_groups`, `scenario_detail` (поля сценария + упорядоченный список игр с `shortDescription`), `game_detail` (игра + `shortDescription` для текущего `scenarioId`), `carousel` из **CR-5**.
- **A-13.** Идентификаторы в deep link и push: **`scenarioId`** (и при необходимости `slug`) — единая трактовка (**БТ FR-M-4, FR-B-2**).

## 6. Мобильное приложение (Flutter)

### 6.1. Утверждения

- **A-14.** Минимальный целевой SDK и политика магазинов соблюдаются на дату релиза; поддержка **iOS и Android** из одной кодовой базы (**БТ §1.1**).
- **A-15.** Навигация: `Home` → `Scenario` → `Game` с сохранением порядка блоков на экране сценария: **сначала** `whyTheseGames`, **затем** список игр (**БТ FR-M-2, версия БТ 0.9**).
- **A-16.** Локализация UI и контента — **только русский** (**БТ §1.1**); форматирование дат/чисел — `ru` locale.
- **A-17.** Онбординг (**БТ UJ-4**): отдельный поток экранов + запрос разрешения на уведомления в контексте ценности; отказ **не блокирует** основной сценарий.
- **A-18.** Шаринг (**БТ FR-M-7**): `share_plus` или платформенный `Share`; в payload — текст + **универсальная ссылка** с UTM; изображение превью — по возможности через ссылку (OG на сайте обеспечивает превью в мессенджерах).
- **A-19.** Deep link: обработка **cold/warm start** через `uni_links` / `app_links` + настройка **Apple Universal Links** и **Android App Links** (**см. раздел 7**).

### 6.2. Офлайн и кэш (**БТ FR-M-3, NFR-1**)

- **A-20.** Включить **Firestore persistence** на мобильных клиентах для кэширования прочитанных документов.
- **A-21.** Для изображений — кэш на диске (`cached_network_image` или эквивалент) с **явным верхним пределом** (**A-21a**).
- **A-22.** При старте: если сеть есть — фоновое обновление; если нет — показ кэша без блокирующей ошибки; опционально индикатор «данные от …» (**БТ §13 риски**).
- **A-21a. (Размер кэша изображений и prefetch)** **App Store и Google Play не задают** фиксированного «разрешённого МБ» для кэша: ограничение — разумное использование диска и отсутствие злоупотреблений. Критерии выбора: (1) объём типичных превью и слайдов карусели; (2) не вытеснять критичные данные пользователя; (3) предсказуемость на слабых устройствах. Для MVP: **потолок дискового кэша изображений 100–150 МБ**, политика **LRU**; **prefetch** обложки/превью **следующей** карточки на витрине — **желательно** (один-два HTTP-запроса на экран), не обязательно для первой итерации.
- **A-45.** **Принудительное обновление:** через **Firebase Remote Config** (или аналог) экспонируются **`min_supported_build`** (и при необходимости **`content_schema_version`**). При несовместимости: блокирующий экран «обновите приложение» **или** сброс локального кэша Firestore + перезагрузка контента при повышении версии схемы — по политике релиза (**A-44**).

### 13.1. Core Web Vitals: таргетные пороги (Google) и позиция Яндекса

**Google** (актуальный публичный стандарт для набора **Core Web Vitals**, см. [Web Vitals](https://web.dev/articles/vitals) и [определение порогов](https://web.dev/articles/defining-core-web-vitals-thresholds)) задаёт для зоны **«хорошо» (good)**:

| Метрика | Порог «хорошо» | Смысл |
|---------|----------------|--------|
| **LCP** (Largest Contentful Paint) | **≤ 2,5 с** | Крупнейший контент виден достаточно быстро |
| **INP** (Interaction to Next Paint) | **≤ 200 мс** | Отклик на действия пользователя (с **марта 2024** INP входит в CWV вместо FID) |
| **CLS** (Cumulative Layout Shift) | **≤ 0,1** | Стабильность вёрстки, без заметных сдвигов |

**Как измерять (важно для приёмки):** Google рекомендует оценивать достижение целей по **75-му перцентилю** (**p75**) **полевых** данных (**field**) — реальные визиты, отдельно **mobile** и **desktop** (например [Chrome UX Report](https://developer.chrome.com/docs/crux) / отчёт Search Console / собственный RUM). **Лабораторные** отчёты (Lighthouse, PageSpeed Insights в режиме симуляции) полезны на этапе разработки, но **не заменяют** поле; **INP** в чистой лаборатории без ввода пользователя **не воспроизводится** — ориентир в лабе часто даёт **TBT** (Total Blocking Time) как косвенный сигнал к INP.

**Яндекс** в открытой документации **не публикует** отдельный набор численных порогов, эквивалентный **Core Web Vitals** от Google, как единый обязательный стандарт для всех сайтов. Для продукта с **русскоязычной** аудиторией и SEO в обеих системах разумно: **(1)** зафиксировать **те же целевые значения**, что и у Google CWV, для страниц **scenario-games.ru**; **(2)** дополнительно смотреть **Яндекс.Метрику** (модуль / отчёты по Web Vitals, если включены) и **показатели скорости** в **Яндекс.Вебмастере** (бета-оценки и т.п.) как **дополнительный** контроль, без подмены методики p75 в поле.

При **изменении** порогов или состава CWV Google публикует обновления на **web.dev** и в changelog метрик — раз в год пересматривать **§13.1** по официальным источникам.

## 17. Критерии готовности MVP (системные)

1. МП читает опубликованный контент с Firebase, отображает витрину и переходы **Home → Scenario → Game** согласно **FR-M-2**.
2. Офлайн: последний успешный кэш открывается без блокирующих ошибок.
3. Push приходит **не чаще одного раза в сутки**, в **11:00 МСК**; при нескольких новинках за окно — открывается **последний** опубликованный сценарий (**A-7a**); тап ведёт на его экран.
4. Шаринг формирует ссылку с UTM; без приложения открывается веб-страница сценария с корректными OG-полями; статические страницы сайта соответствуют **SR-SEO-1**.
5. Аналитика фиксирует переходы, открытия сценариев с источником и block-view по согласованным порогам; выполняются **SR-PRIV-1–5**; политика конфиденциальности и тексты — **SR-PRIV-5**.
6. Security rules исключают утечку черновиков.
7. **Remote Config** и проверка **min_supported_build** / **content_schema_version** реализованы; при критической несовместимости показывается блокирующее обновление или принудительный сброс кэша (**A-45**).
8. Push о новых сценариях: **SR-PUSH-1** (topic `new_scenarios`), подписка из МП после разрешения на уведомления.
9. Выполняются **NFR-SR-7** и **NFR-SR-8** (адаптивность МП и сайта; ориентиры **§6.3**, **§8.2**).
