# Применение flutter-architecture (mad-agents-skills): MVVM + feature-first границы слоёв

## Ценность

Skill **`flutter-architecture`** из [mad-agents-skills](https://github.com/MADTeacher/mad-agents-skills) задаёт конкретный контракт: Views тонкие и декларативные, ViewModels владеют состоянием и командами, Repositories — единственный источник правды, Services — stateless-обёртки внешних источников; правило зависимостей «нижние слои не зависят от верхних» и запрет cross-feature импортов реализации. Эта стори применяет его к МП, чтобы зафиксировать границы слоёв и проверяемый процесс ревью, а не разовый рефакторинг «на глаз».

> ⚠️ Пересекается с **US-E12-01** (`flutter-apply-architecture-best-practices`). Стори не должна дублировать тот же рефакторинг: согласовать порядок — сначала одна из них задаёт целевую структуру, вторая приносит уточнения (feature-first, DI, Result/Command, offline-first) и проверку.

## Детали поведения

- Запустить skill и следовать его инструкциям:
  ```bash
  npx skills use "https://github.com/madteacher/mad-agents-skills" --skill "flutter-architecture"
  ```
- **Прочитать полный вывод скилла** (при необходимости сначала перенаправить его в временный файл).
- **Относительные пути резолвить от каталога supporting-files**, который вернёт скилл (а не от корня проекта).
- Skill работает по «Core Contract»: сначала инспектировать `pubspec.yaml`, `lib/`, текущие state-management/routing/DI/networking/persistence/test-конвенции, затем принять решения. Применить к проекту:
  - Выбрать структуру: **feature-first** (для средних/крупных приложений и командной работы) vs layer-first; обосновать выбор.
  - Слои: UI (Views + ViewModels), Data (Repositories + Services), Domain — только при сложной/переиспользуемой бизнес-логике.
  - Правило зависимостей: нижние слои не зависят от верхних; ViewModels могут обращаться к Repository напрямую; cross-feature импорты реализации запрещены (общее — в `shared/` или через интерфейсы/DI).
  - Осмысленно применять паттерны при необходимости: Repository, Result, Command, DI, offline-first/optimistic UI — **не добавлять папки ради диаграммы**.
  - Сохранять существующие конвенции проекта, если они не противоречат явному архитектурному требованию.
- Для review-задачи skill требует сначала докладывать о нарушениях слоёв, cross-feature импортах и проблемах владения состоянием — учесть, если стори ведётся как аудит.
- Валидация: `flutter analyze`, сфокусированные `flutter test`; при копировании шаблонов (`command.dart`, `result.dart`) — `dart format --output=none --set-exit-if-changed`.
- **Поведение не меняется:** навигация, контент, офлайн-кэш, аналитика, push, шаринг и Crashlytics работают как раньше.

## Вне scope

- Новая функциональность и изменение UI/UX.
- Реализация конкретных шаблонов из скилла (Result/Command), если в проекте уже есть эквивалент.
- Рефакторинг сайта (`scenario-site/`).

## Критерии приёмки (AC)

- **AC-01**
  - Given репозиторий `scenario`
  - When выполнен запуск `npx skills use "https://github.com/madteacher/mad-agents-skills" --skill "flutter-architecture"` и прочитан его полный вывод
  - Then инструкции скилла применены, относительные пути резолвятся от supporting-files.

- **AC-02**
  - Given кодовая база МП
  - When завершено применение скилла
  - Then выбранная структура (feature-first/layer-first) обоснована, границы слоёв соблюдены, Views тонкие, ViewModels владеют состоянием, Repositories — SSOT, Services stateless, cross-feature импортов реализации нет.

- **AC-03**
  - Given внесённые изменения
  - When запущены `flutter analyze` и `flutter test`
  - Then ошибок нет, тесты зелёные, регрессов поведения нет.
