# Применение flutter-apply-architecture-best-practices: слоистая архитектура lib/

## Ценность

Сейчас `lib/` растёт «плоским» способом: фичи (`lib/features/*`), данные (`lib/data/*`), дизайн (`lib/design/*`), аналитика (`lib/analytics/*`), кэш (`lib/cache/*`) соседствуют без явного разделения слоёв. Отсутствуют ViewModel-слой (состояние и презентационная логика живут прямо в виджетах) и единый репозиторный контракт. Это затрудняет точечные изменения и тестирование.

Эта стори применяет официальный skill Flutter **`flutter-apply-architecture-best-practices`** и приводит кодовую базу МП к рекомендованному слоистому подходу (UI / Logic / Data; MVVM + Repository), не меняя пользовательское поведение.

## Контекст и трассировка

| ID | Документ / ссылка | Как используется в этой стори |
|----|-------------------|-------------------------------|

Трассировки на БТ/СТ у истории нет: это внутренняя работа по техдолгу.

## Детали поведения

- Запустить skill и следовать его инструкциям:
  ```bash
  npx skills use "https://github.com/flutter/agent-plugins" --skill "flutter-apply-architecture-best-practices"
  ```
- **Прочитать полный вывод скилла** (при необходимости сначала перенаправить его в временный файл, чтобы ничего не потерялось).
- **Относительные пути резолвить от каталога supporting-files**, который вернёт скилл (а не от корня проекта).
- Применить рекомендованную структуру к `lib/`:
  ```text
  lib/
  ├── data/
  │   ├── models/         # API/contract models
  │   ├── repositories/   # реализации репозиториев
  │   └── services/       # Firestore/Supabase/HTTP-обёртки, кэш, платформенные плагины
  ├── domain/
  │   ├── models/         # чистые доменные модели
  │   └── use_cases/      # (опционально) бизнес-логика
  └── ui/
      ├── core/           # общие виджеты, тема, типографика (из lib/design/)
      └── features/
          └── [feature]/
              ├── view_models/
              └── views/
  ```
- Ввести **ViewModel** (расширяет `ChangeNotifier`/`Listenable`) на фичу: состояние и пользовательские действия — в ViewModel, виджеты остаются «тонкими» и получают данные через конструктор/`ListenableBuilder`.
- Ввести **Repository** как единый источник правды: сервисы — stateless-обёртки внешних API, репозитории возвращают доменные модели и отвечают за кэш/офлайн.
- **Поведение не меняется:** навигация, контент, офлайн-кэш, аналитика, push, шаринг и Crashlytics работают как раньше.
- Запускать валидацию после каждого шага (`flutter analyze`, `flutter test`) — правки идемпотентны и не оставляют дерево красным.

## Вне scope

- Новая функциональность и изменение UI/UX.
- Смена пакетов контракта (`lib/data/contract/*`) по существу — допускается только перемещение/обёртка.
- Рефакторинг сайта (`scenario-site/`) — эпик E12 про МП.

## Критерии приёмки (AC)

- **AC-01**
  - Given репозиторий `scenario`
  - When выполнен запуск `npx skills use ... --skill "flutter-apply-architecture-best-practices"` и прочитан его полный вывод
  - Then инструкции скилла применены, относительные пути резолвятся от supporting-files.

- **AC-02**
  - Given код в `lib/`
  - When завершён рефакторинг
  - Then структура соответствует слоям скилла (`lib/ui`, `lib/domain`, `lib/data`), а UI отделён от логики (ViewModel) и доступа к данным (Repository).

- **AC-03**
  - Given пользовательское поведение МП
  - When запущены `flutter analyze` и `flutter test`
  - Then ошибок нет, тесты зелёные, регрессов поведения нет.

## Зависимости и блокеры

- Доступ в сеть для `npx skills use` (загрузка скилла с `github.com`).
- Node.js/npx в окружении разработчика.
- Рефакторинг крупный: вести инкрементально, начиная с одной фичи, чтобы не блокировать другие задачи.
