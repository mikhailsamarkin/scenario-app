# Создание игры с каруселью и валидацией полей

## Ценность

Игра — атом контента для подборок; карусель и enum-поля должны соответствовать контракту, чтобы МП и сайт показывали предсказуемый UI без релиза клиента при смене данных.

## Контекст и трассировка

| ID | Документ | Как используется в этой стори |
|----|----------|-------------------------------|
| CR-4, CR-4.1, CR-5 | БТ | Состав игры, enum, карусель |
| A-29, A-29a | СТ | Запись в Firestore + Storage; без отдельной CMS на старте |
| A-30 | СТ | Валидация enum и обязательных полей |
| ED-4 | ED | Контент через репозиторий и скрипты, не админка |
| ED-7 | ED | Upload изображений в Storage |

## Детали поведения

- Создание/редактирование игры: карусель с допустимыми типами слайдов, alt для медиа, минимум один слайд типа `teaser` (**CR-5**, **A-30**).
- Значения enum только из разрешённых ключей (**CR-4.1**).
- Публикация в Firestore (+ файлы в Storage по **A-29a**, **ED-7**).
- На раннем этапе путь эксперта — импорт из репозитория (**ED-4**), поведение данных эквивалентно «создать игру».

## Вне scope

- Отдельная веб-админка (вне **ED-4** на текущем этапе).
- Верстка сайта (E4).

## Критерии приёмки (AC)

- **AC-01** *(БТ CR-5, СТ A-30)*  
  - Given новая игра  
  - When сохраняется карусель  
  - Then есть минимум один слайд `teaser` и валидные типы слайдов.

- **AC-02** *(БТ CR-4.1)*  
  - Given поля с enum  
  - When записываются значения  
  - Then только ключи из допустимого набора (как в контракте).

- **AC-03** *(СТ A-29)*  
  - Given опубликованная игра  
  - When клиенты читают публичное представление  
  - Then данные доступны согласно правилам публичного read.

## Зависимости и блокеры

- **E0:** схема и правила для игр/медиа.
- Storage rules и пути загрузки (**ED-7**).

## Открытые вопросы

- Нет.

## Примечания для downstream

- Тексты клиентских полей: plain text и переносы `\n` там, где это задано (**СТ A-4a**) для связанных текстовых полей игры.
