# Тест-кейсы: Схема коллекций и публичных агрегатов для единого контракта МП и Next.js

## Обзор

- Цель: проверить, что черновики недоступны публичному read, публичные агрегаты соответствуют зафиксированному контракту и что витрина (`home_feed` или эквивалент) описана без недокументированных полей.
- Вне scope: полная реализация SSG (E4), бизнес-логика импорта контента сверх требований к данным.

## Матрица трассировки AC → тест-кейсы

| AC    | TC-ID        | Кратко |
|-------|--------------|--------|
| AC-01 | TC-01, TC-02 | Read черновика запрещён; опубликованный доступен |
| AC-02 | TC-03, TC-04 | Имена/поля агрегатов совпадают с документом схемы и СТ §4 |
| AC-03 | TC-05        | Структура home_feed достаточна для главного экрана МП |

## Тест-кейсы

### TC-01 — Черновик сценария недоступен публичному клиенту

| Поле | Значение |
|------|----------|
| **Приоритет** | P0 |
| **Слой** | integration |
| **Покрывает** | AC-01 |
| **Тип** | negative |

**Предусловия:** В Firestore есть документ сценария в статусе черновика (без публикации в публичное представление); используется клиент/эмулятор с правами анонимного или публичного приложения.

**Тестовые данные:** Идентификатор черновика из тестового окружения.

**Шаги**

1. Выполнить read по публичному пути к данным сценария для черновика (как в правилах безопасности).
2. Зафиксировать код ответа / отсутствие документа.

**Ожидаемый результат:** Данные черновика не возвращаются (permission denied / документ отсутствует согласно правилам).

**Заметки для автоматизации:** Firebase emulator + rules unit tests; не хранить сервисные ключи в репозитории.

---

### TC-02 — Опубликованный сценарий читается публичным клиентом

| Поле | Значение |
|------|----------|
| **Приоритет** | P0 |
| **Слой** | integration |
| **Покрывает** | AC-01 |
| **Тип** | positive |

**Предусловия:** Сценарий опубликован и доступен через публичный агрегат/путь.

**Тестовые данные:** ID опубликованного сценария.

**Шаги**

1. Запросить публичное представление опубликованного сценария тем же типом клиента, что в TC-01.
2. Сверить наличие ожидаемых полей по контракту.

**Ожидаемый результат:** Документ успешно читается; структура соответствует схеме.

**Заметки для автоматизации:** Отдельная фикстура «опубликовано» в seed-скриптах.

---

### TC-03 — Соответствие имён коллекций и документов документу схемы

| Поле | Значение |
|------|----------|
| **Приоритет** | P0 |
| **Слой** | contract / api |
| **Покрывает** | AC-02 |
| **Тип** | positive |

**Предусловия:** Зафиксирован единый документ схемы (репозиторий); список публичных путей известен.

**Тестовые данные:** Таблица ожидаемых имён коллекций/полей.

**Шаги**

1. Для каждого публичного агрегата из документа схемы выполнить чтение тестовым клиентом.
2. Сверить имена коллекций и ключи верхнего уровня с документом и СТ §4.

**Ожидаемый результат:** Нет расхождений имён и семантики полей.

**Заметки для автоматизации:** JSON Schema / snapshot-тесты против экспортированного примера; версионировать схему.

---

### TC-04 — Отсутствие недокументированных обязательных полей в ответе

| Поле | Значение |
|------|----------|
| **Приоритет** | P1 |
| **Слой** | contract |
| **Покрывает** | AC-02 |
| **Тип** | edge |

**Предусловия:** Контракт описывает набор полей для публичного read.

**Тестовые данные:** Эталонный JSON из документации.

**Шаги**

1. Получить реальный ответ API/Firestore для эталонного документа.
2. Проверить, что все поля, используемые клиентами, перечислены в документе схемы (обратная проверка: новые поля в данных → обновление схемы).

**Ожидаемый результат:** Клиент может опереться только на документ схемы; расхождения зафиксированы в ADR при изменении.

**Заметки для автоматизации:** allowlist полей в CI.

### TC-05 — home_feed (или эквивалент) покрывает сценарии витрины

| Поле | Значение |
|------|----------|
| **Приоритет** | P0 |
| **Слой** | integration |
| **Покрывает** | AC-03 |
| **Тип** | positive |

**Предусловия:** В данных есть минимум один сценарий для витрины; агрегат витрины заполнен.

**Тестовые данные:** Выборка из тестового `home_feed`.

**Шаги**

1. Прочитать документ/коллекцию `home_feed` (или эквивалент по СТ).
2. Проверить наличие полей, достаточных для карточки на главном экране (идентификатор, заголовок, порядок, признаки витрины — по контракту).

**Ожидаемый результат:** МП может построить главный экран без дополнительных недокументированных запросов к черновикам.

**Заметки для автоматизации:** Синхронизировать с контрактными тестами МП (mock JSON).
