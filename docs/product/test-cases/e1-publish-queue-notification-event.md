# Тест-кейсы: Очередь уведомлений при первой публикации сценария

## Обзор

- Цель: проверить создание события в очереди при первой публикации, отсутствие дубликата при правке только состава игр и готовность формата данных без FCM.
- Вне scope: полный push и scheduler (E3) — при срезе без push приёмка по очереди и флагам.

## Матрица трассировки AC → тест-кейсы

| AC    | TC-ID        | Кратко |
|-------|--------------|--------|
| AC-01 | TC-01        | Событие в очереди после первой публикации |
| AC-02 | TC-02        | Смена только игр не создаёт новое событие «новинка» |
| AC-03 | TC-03        | Формат записи готов к E3 без миграции |

## Тест-кейсы

### TC-01 — Первая публикация сценария создаёт запись в очереди

| Поле | Значение |
|------|----------|
| **Приоритет** | P0 |
| **Слой** | integration |
| **Покрывает** | AC-01 |
| **Тип** | positive |

**Предусловия:** Сценарий никогда не был опубликован; триггер Cloud Function/пайплайна включён в тестовом окружении.

**Тестовые данные:** ID сценария.

**Шаги**

1. Выполнить первую публикацию сценария.
2. Прочитать коллекцию/очередь уведомлений (по A-31).

**Ожидаемый результат:** Появилась запись/событие, связанное с этим сценарием и типом «новинка дня» (или согласованный тип).

**Заметки для автоматизации:** Эмулятор functions или staging; идемпотентный cleanup.

---

### TC-02 — Изменение только порядка/состава игр у опубликованного сценария

| Поле | Значение |
|------|----------|
| **Приоритет** | P0 |
| **Слой** | integration |
| **Покрывает** | AC-02 |
| **Тип** | negative |

**Предусловия:** Сценарий уже был опубликован; в очереди уже есть или был учтён первый ивент (фиксация начального состояния).

**Тестовые данные:** Новый порядок игр без «републикации как новой версии» по продуктовой логике.

**Шаги**

1. Зафиксировать количество/идентификаторы событий в очереди до изменения.
2. Обновить только состав/порядок игр и сохранить.
3. Проверить очередь.

**Ожидаемый результат:** Новое событие «новинка дня» для push не создано (A-33).

**Заметки для автоматизации:** Уточнить в коде критерий «только игры» — тест должен совпадать с триггером.

---

### TC-03 — Запись очереди валидируется схемой для будущего FCM

| Поле | Значение |
|------|----------|
| **Приоритет** | P1 |
| **Слой** | contract |
| **Покрывает** | AC-03 |
| **Тип** | positive |

**Предусловия:** Задокументирована JSON-схема payload очереди (ED-11).

**Тестовые данные:** Пример записи из TC-01.

**Шаги**

1. Прогнать запись через валидатор схемы, ожидаемый E3 (scenarioId, timestamps и т.д.).
2. Убедиться, что поля достаточны для scheduler и deep link без переделки формата.

**Ожидаемый результат:** Валидация проходит; при включении E3 не требуется миграция формата.

**Заметки для автоматизации:** Общая JSON Schema в репозитории.

---

## Регресс и смоук

- **Smoke:** TC-01.
- **Регресс полный:** TC-01–TC-03 при изменении триггеров публикации или A-31/A-33.

## Допущения

- Определение «первая публикация» vs «републикация» зафиксировано в коде триггера (см. открытые вопросы стори).

## Открытые вопросы

- Уточнение «первая публикация» при реализации — синхронизировать с PO при расхождении с ожиданиями.
