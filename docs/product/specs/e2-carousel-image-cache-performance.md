# Спецификация реализации — US-E2-06 «Производительность карусели и кэш изображений»

## 1. Scope

**В объёме:**

* **Дисковый кэш изображений** карусели с **явным верхним пределом по числу объектов** и политикой **LRU** (вариант B, **ADR-004–009**). Отклонение от байтового потолка **A-21a** (100–150 МБ) — решение tech lead: лимит по числу объектов (`cached_network_image`/`flutter_cache_manager`), см. §6 Риски.

* **Повторное использование кэша** при повторном открытии игры: изображения не грузятся заново с сети, если они в пределах лимита диска (**AC-01**, **A-21**).

* **Плавность листания** карусели без систематических фризов на целевых устройствах (**AC-02**, **NFR-1**, **NFR-SR-6**).

* **Согласование выбора библиотеки кэша** с tech lead (**ED-6**, **ED-13**, **ADR-004–009**) — как блокер/предусловие, а не самостоятельный выбор агента.

* **Prefetch** обложки/превью следующей карточки — **желательно**, не обязательно для первой итерации (**A-21a**).

* **Тесты**: unit-тесты кэша/виджета (TC-01, TC-03), ручная проверка плавности (TC-02).

**Вне scope:**

* Полная оптимизация всего приложения вне карусели (стори).

* Реализация самого экрана игры и карусели — **US-E2-03** (зависимость; здесь — только производительность и кэш поверх готовой карусели).

* Офлайн-доступ к контенту и Firestore persistence — **US-E2-05** (**A-20–A-22**); здесь затрагивается только дисковый кэш изображений.

* Обновление контента при сети — **US-E2-04**.

* Оптимизация веса/размеров изображений на стороне контента — **NFR-SR-4** (гайдлайн контента, **CR-5**).

**Ключевые решения:**

* **Кэш на диске с верхним пределом по числу объектов** (**ADR-004–009**, вариант B): `cached_network_image` 4.x + `flutter_cache_manager`; лимит — `maxNrOfCacheObjects` (LRU по последнему использованию). Байтовый потолок **A-21a** (100–150 МБ) не применяется — см. §6 Риски.

* **Библиотека выбрана** (**ED-6**, **ED-13**, **ADR-004–009**): **`cached_network_image` 4.x** (виджет + placeholder/error) поверх `flutter_cache_manager`; лимит — по числу объектов. Решение зафиксировано в ADR-004–009.

* **Источник изображений — Supabase Storage** (**ED-14**, **A-39**): `Slide.imageRef` — путь объекта `games/{id}/<file>`; публичный URL — по правилу `supabasePublicUrl(path)`. Кэш работает поверх публичных URL, контракт данных не меняется.

* **Кэш не трогает данные пользователя** (**A-21a**): LRU-вытеснение затрагивает только кэш изображений; критичные данные пользователя не вытесняются.

## 4. Шаги (в порядке зависимостей)

### Шаг 1. Зафиксировать выбор библиотеки кэша

* **Решено (ADR-004–009):** пакет — **`cached_network_image` 4.x** (вариант B), лимит — **по числу объектов** (`maxNrOfCacheObjects`), политика LRU. Запись внесена в `docs/engineering-decisions-and-open-questions.md`.

* Критерии (по **A-21a**): (1) объём типичных превью и слайдов карусели; (2) не вытеснять критичные данные пользователя; (3) предсказуемость на слабых устройствах.

### Шаг 2. Интеграция дискового кэша изображений

* **Реализовано:** политика LRU-кэша с лимитом размера — `scenario/lib/cache/lru_cache.dart` (`LruCache`, `kImageCacheDefaultMaxBytes = 150 МБ`). Чистый Dart, не зависит от пакета (ED-13); покрыта unit-тестами `scenario/test/lru_cache_test.dart` (TC-01, TC-03).

* **Реализовано:** обёртка над `cached_network_image` — `scenario/lib/cache/cached_network_image_widget.dart` (`CachedNetworkImageWidget`), принимает публичный URL (`supabasePublicUrl(imageRef)`, **A-39**), placeholder и errorWidget. Зависимость `cached_network_image: ^4.0.0` добавлена в `pubspec.yaml` (ADR-004–009).

* Параметры кэша (**ADR-004–009**): лимит — **по числу объектов** (`maxNrOfCacheObjects`), политика **LRU**; конфигурируемо (для тестов и dev — низкий лимит).

* Поведение: при наличии изображения в кэше в пределах лимита — чтение с диска без сетевого запроса (**AC-01**, **R2**); при отсутствии — загрузка и запись в кэш; при превышении лимита — LRU-вытеснение (**R6**).

* **Prefetch** (**A-21a**, **R5**): опционально, один-два HTTP-запроса на экран для обложки/превью следующей карточки; не обязательно для первой итерации.

### Шаг 3. Применение в карусели экрана игры

* Зависит от **US-E2-03** (экран игры с каруселью). В этой стори карусель использует кэшируемый виджет из шага 2 для слайдов `GamePublic.carousel` (`Slide.imageRef`).

* **Плавность листания** (**AC-02**, **NFR-1**, **NFR-SR-6**): изображения из кэша не блокируют листание; проверка по чеклисту QA на целевых устройствах. Пороги приёмки (индустриальные стандарты): устойчивое листание ≥ 55 FPS (P95 время кадра ≤ 18 мс), доля пропущенных кадров < 5% за 20 свайпов вперёд-назад; целевые устройства — среднебюджетный Android (Snapdragon 7-й серии, напр. Pixel 6a) и актуальный iPhone (13+), портрет.

### Шаг 4. Тесты

| TC    | Слой        | Проверка                                                       | Где                              |
| ----- | ----------- | -------------------------------------------------------------- | -------------------------------- |
| TC-01 | integration | Повторное открытие — изображения из кэша (0 HTTP при офлайн)   | unit кэша + ручная проверка      |
| TC-02 | manual-only | Листание без систематических фризов: ≥ 55 FPS (P95 ≤ 18 мс), < 5% пропущенных кадров за 20 свайпов | QA-чеклист на целевых устройствах |
| TC-03 | integration | Лимит диска: LRU-вытеснение старых изображений, кэш не растёт  | unit кэша с низким лимитом в dev |

* Unit-тесты кэша (TC-01, TC-03): повторное чтение не делает сетевой запрос; при превышении лимита вытесняются старые (LRU); кэш не растёт бесконечно.

* TC-02 — ручная проверка плавности; автоматизация (FPS/perf overlay) — опционально, пороги в CI по профайлеру.

## 6. Риски

* **Отклонение от байтового потолка A-21a (100–150 МБ)** — выбран лимит **по числу объектов** (вариант B, ADR-004–009). Митиг: `maxNrOfCacheObjects` + LRU не дают бесконечного роста; разумное число объектов подобрано под типичный объём превью/слайдов (критерий A-21a п.1); магазины приложений не задают фиксированного лимита. При необходимости — пересмотр в ADR.

* **Экран игры/карусель не реализован** (**US-E2-03**) — шаг 3 невозможен до его завершения. Митиг: шаг 2 (кэш-виджет) реализуется и тестируется независимо; интеграция — после US-E2-03.

* **Пороговые устройства и FPS** — зафиксированы как индустриальные стандарты (≥ 55 FPS / P95 ≤ 18 мс / < 5% пропущенных кадров; устройства — среднебюджетный Android и актуальный iPhone). Остаётся подтвердить на реальных устройствах в QA-плане.

* **Кэш растёт бесконечно / вытесняет данные пользователя** (**A-21a**). Митиг: жёсткий предел по числу объектов + LRU; кэш изолирован от данных пользователя.

## 9. Verify

Соответствие критериям приёмки **US-E2-06**:

* **AC-01 (A-21a)** — TC-01/TC-03: при повторном открытии игры изображения берутся из кэша в пределах лимита (0 сетевых запросов при офлайн); при превышении лимита по числу объектов — LRU-вытеснение, кэш не растёт бесконечно.

* **AC-02 (NFR-SR-6, NFR-1)** — TC-02: листание карусели без систематических фризов — ≥ 55 FPS (P95 ≤ 18 мс), < 5% пропущенных кадров за 20 свайпов на целевых устройствах (среднебюджетный Android / актуальный iPhone, портрет).

Критерий готовности: кэш-виджет на `cached_network_image` с лимитом по числу объектов и LRU реализован и покрыт unit-тестами (TC-01, TC-03); интеграция в карусель экрана игры (после US-E2-03) не даёт систематических фризов (TC-02).
