# Use cases и user stories: Scenario (S)

**Версия документа:** 1.4  
**Роль автора:** senior product manager (декомпозиция для инкрементальной доставки)  
**Источники:** [Функциональные и бизнес-требования](functional-and-business-requirements.md) (БТ), [Системные требования](system-requirements.md) (СТ)  
**Назначение:** список артефактов уровня продукта, на которые команда разработки может нарезать бэклог и релизы так, чтобы каждый инкремент по возможности давал проверяемую ценность для пользователя или бизнеса.

**Согласованный минимальный первый релиз (PO):** мобильное приложение и контентный контур **без** публичного сайта и **без** push; **без** групп смысла и раздела «Сценарии прошлого» (эпики E4, E3-push, E7 откладываются). Полный чеклист **СТ §17** остаётся целевым для «расширенного» релиза.

---

## 1. Принципы инкрементальной доставки

1. **Сначала источник правды и чтение контента.** Без опубликованных данных в едином хранилище (Firestore + правила) нельзя честно закрыть основной job-to-be-done в МП и на сайте (**БТ BR-2, BR-3**; **СТ A-2, A-4**).
2. **Вертикальные срезы по каналам.** Один инкремент предпочтительно закрывает сквозной сценарий: данные → МП **или** данные → сайт, а не «только бэкенд без UI» без демо.
3. **Целевой MVP по СТ §17** — северная звезда для «полного» продукта (сайт, push, шаринг с веб-fallback и т.д.). **Минимальный первый релиз** может намеренно не включать часть эпиков (**см. шапку документа**); критерии приёмки такого релиза фиксируются отдельным списком (E0, E1, E2, онбординг без обязательного push, E5/E6 — по решению бэклога).
4. **Зависимости явно выносить в «блокеры».** Например: домен `scenario-games.ru`, SSL, файлы AASA/assetlinks — для шаринга и deep link (**СТ A-23–A-25**). Юридические инструменты (CMP, cookie и т.д.) — **вне [системных требований](system-requirements.md) §11.3**, не блокируют инженерный контур по **SR-PRIV-1–5**.

## 3. Use cases (верхний уровень)

Формат: **UC-ID** — актор — цель — краткий основной поток — трассировка.

### UC-01. Просмотреть подборку игр под жизненную ситуацию (МП)

- **Актор:** конечный пользователь МП.  
- **Цель:** быстро получить ограниченный осмысленный список игр через сценарий (**БТ BR-1, UJ-1**).  
- **Основной поток:** открыть МП → главный экран (витрина) → выбрать сценарий → прочитать «почему эти игры подходят» → просмотреть состав подборки → открыть игру → просмотреть карусель, 4 характеристики, краткое описание в контексте сценария (**БТ FR-M-2**).  
- **Трассировка:** FR-M-1, FR-M-2, FR-M-3, CR-4, CR-4.1, CR-5.

### UC-02. Опубликовать и актуализировать кураторский контент (эксперт)

- **Актор:** эксперт / владелец контента.  
- **Цель:** управлять сценариями, играми, порядком, витриной, медиа и текстами шаринга без программирования (**БТ FR-B-6**).  
- **Основной поток:** войти в админку/CMS → создать/отредактировать игру (карусель, enum-поля) → создать сценарий (`whyTheseGames`, мета, витрина) → связать игры с порядком и `shortDescription` → опубликовать → данные доступны МП и сайту (**БТ FR-B-1, FR-B-3**).  
- **Трассировка:** FR-B-1, FR-B-6; **СТ** A-29–A-30, валидация обязательных полей.

### UC-03. Найти сценарий или игру через поисковик (посетитель сайта)

- **Актор:** посетитель сайта (органика).  
- **Цель:** получить ответ на запрос и познакомиться с брендом; при желании — установить МП (**БТ UJ-2, BR-5**).  
- **Основной поток:** переход из поиска на страницу сценария или игры → чтение согласованного контента → перелинковка → CTA в сторы (**БТ FR-W-2, FR-W-3**).  
- **Трассировка:** FR-W-1–FR-W-3, NFR-2; **СТ** SR-SEO-1.

### UC-04. Узнать о новом сценарии и открыть его из уведомления

- **Актор:** пользователь с установленным МП и разрешёнными уведомлениями.  
- **Цель:** не пропустить новую подборку (**БТ UJ-3, BR-4**).  
- **Основной поток:** публикация нового сценария → в 11:00 МСК одно уведомление на topic → тап → deep link на экран сценария (**БТ FR-M-4**).  
- **Трассировка:** FR-B-4, FR-M-4; **СТ** A-7a, SR-PUSH-1, A-31–A-32.

### UC-05. Поделиться сценарием с друзьями

- **Актор:** пользователь МП.  
- **Цель:** отправить ссылку на сценарий в мессенджер; получатель открывает приложение или сайт (**БТ FR-M-7, FR-W-4**).  
- **Основной поток:** экран сценария → «Поделиться» → системный share → URL с UTM → у получателя: приложение или веб с OG (**БТ FR-M-7**).  
- **Трассировка:** FR-M-7, FR-W-4; **СТ** A-23–A-25.

### UC-06. Первый запуск приложения

- **Актор:** новый пользователь МП.  
- **Цель:** понять ценность продукта и начать пользоваться; опционально включить уведомления (**БТ UJ-4**).  
- **Основной поток:** установка → онбординг (ценность + как пользоваться) → запрос push в контексте → первая загрузка контента или сообщение при офлайне (**БТ FR-M-3**).  
- **Трассировка:** UJ-4, A-17 (СТ).

### UC-07. Использовать приложение без сети

- **Актор:** пользователь МП.  
- **Цель:** просмотреть уже загруженные сценарии и игры (**БТ FR-M-3**).  
- **Основной поток:** запуск без сети → показ кэша Firestore и изображений без блокирующей ошибки.  
- **Трассировка:** FR-M-3; **СТ** A-20–A-22, NFR-SR-3.

| **МП + Firestore без push и без сайта** | E0, E1, E2 | Закрывает core JTBD; нет органики и реактивации (**BR-4, BR-5**). |
| **Сайт без МП** | E0, E1, E4 | Редко имеет смысл как продуктовый релиз при стратегии «сайт ведёт в МП», но возможен как технический инкремент. |

## 6. Решения владельца продукта и каталог метрик

### 6.1. Зафиксированные решения

| Тема | Решение |
|------|---------|
| **Редактор контента** | Запись **напрямую в Firestore + Storage**; вариант UI — ADR (**СТ A-29a**; [engineering-decisions-and-open-questions.md](engineering-decisions-and-open-questions.md) §3). |
| Сайт в первом релизе | **Не входит** — откладывается (эпик E4). |
| Push в первом релизе | **Не входит** — откладывается (часть E3: только онбординг без обязательной подписки на topic / без Cloud Scheduler-пушей). |
| Группы смысла и «Сценарии прошлого» (E7) | **Не входят** в первый релиз — запуск без них. |

### 6.2. Каталог метрик из БТ §11.1 (выбрать 3–5 KPI для go/no-go)

Ниже — **полный перечень** ориентиров для дашбордов из [функциональных требований §11.1](functional-and-business-requirements.md). Точные определения (событие = метрика) задаются при внедрении аналитики. Часть пунктов **не применима**, пока нет сайта, push, групп или поиска — помечено *отложено*.

**Вовлечение и аудитория МП**

1. Установки  
2. **DAU / WAU / MAU** (или аналог по выбранному инструменту)  
3. **Удержание** после первого открытия: **D1, D7, D30**  
4. **Сессии** на пользователя  
5. Средняя **длительность сессии**

**Навигация и контент (все клики/переходы — FR-M-6)**

6. Просмотры **главного экрана** (витрина)  
7. Просмотры **групп смысла** — *отложено до E7*  
8. Просмотры **«Сценарии прошлого»** — *отложено до E7*  
9. **Открытия сценария** с разбивкой по источнику: витрина / группа / прошлое / push / поиск — для первого релиза актуальны витрина и прочие реализованные источники (push/groups/past/search — по мере появления)  
10. **Открытия экрана сценария** как целого: в т.ч. взаимодействие с блоком «почему эти игры подходят» и составом подборки  
11. **Открытия экрана игры** (по сценарию и id игры)  
12. **Глубина просмотра:** сколько игр за сессию  
13. **Достижение блоков** («дошёл до блока X») на экране сценария и игры — доли сессий/пользователей, распределение по блокам

**Популярность сценариев (отдельный срез — BR-7)**

14. Число **открытий по каждому id сценария** за период  
15. **CTR** сценария на витрине (показ → открытие), *если технически доступно*  
16. Рейтинг **«топ сценариев»** для будущего пересмотра порядка на витрине

**Контент и стабильность**

17. Успех / ошибка **синхронизации контента** с бэкенда  
18. Доля сессий с **устаревшим кэшем**  
19. **Открытия из push** и конверсия «получил push → открыл сценарий» — *отложено до push*

**Шаринг сценария (FR-M-7)**

20. **Попытки поделиться** (тап по «Поделиться»)  
21. **Успешный вызов системного share** (лист открыт, пользователь выбрал канал)  
22. **Конверсия по UTM** на целевой URL сценария — *смысл полный при веб-fallback и аналитике сайта; до сайта — ограниченно*

**Сайт** — *весь блок отложен до E4*

23. Органический **трафик** (сессии, пользователи) по страницам сценариев и игр  
24. **Клики по CTA «установить МП»** и переходы в сторы  
25. **Скорость загрузки** страниц (Core Web Vitals или аналог)

**Дополнительно (системный уровень, не дублирует §11.1, но полезно для приёмки)**

- **Crash-free users / sessions** (Firebase Crashlytics — **СТ A-41**)  
- Алерты по ошибкам Cloud Functions / Scheduler — *актуально при push и фоновых задачах*

### 6.4. Решения и пояснения

| Тема | Решение / смысл |
|------|-----------------|
| **Редактор контента** | Отдельная CMS **не используется**; см. **СТ A-29, A-29a** и [engineering-decisions-and-open-questions.md](engineering-decisions-and-open-questions.md) §3. |

## 7. Проверка user stories по INVEST

**INVEST:** **I**ndependent — **N**egotiable — **V**aluable — **E**stimable — **S**mall — **T**estable.

Ниже — оценка каждой истории из **§4**; «⚠» — риск или условие, «✓» — в целом ок для бэклога при уточнении в скобках.

| ID | I | N | V | E | S | T | Замечания |
|----|---|---|---|---|---|---|-----------|
| US-E0-01 | ⚠ | ✓ | ✓ | ⚠ | ⚠ | ✓ | Крупновата: разбить на «схема Firestore + правила read черновиков» и «публичные агрегаты для МП»; **I** повышается после разбиения. |
| US-E0-02 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | — |
